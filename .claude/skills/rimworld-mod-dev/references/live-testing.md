# Driving the game: GABS, RimBridgeServer and the scenario suite

## The pieces

- **RimBridgeServer** (v2.5.0, the Workshop item 3727949765; until 2026-11-28 a local copy in `RimWorld\Mods`, which BridgeTools now no longer compiles against): a mod that exposes the running game as tools (`rimworld/*`, `rimbridge/*`) over GABP, and loads companion DLLs from `RimWorld\BridgeTools\*`. Ours is `tools/BridgeTools`, which adds `ordo/*`.
- **GABS** (v1.1.2, `~/.gabs/gabs.exe`, config `~/.gabs/config.json`): launches the game and mirrors the bridge's tools into MCP. It's registered as the local-scope MCP server `gabs`. Neither lives in the repo.
- Start with `games_status` or `games_list`, then `games_start` (game id `rimworld`, with a profile) and `games_connect`. For game tools, call `games_tool_names` with `brief: true`, inspect one with `games_tool_detail`, and call it with `games_call_tool`. If an `ordo/*` tool seems missing, reconnect or retry `games_tool_names` before assuming it is.
- `games_status` gives the game's PID as `gamePid`.

## Profiles

Each GABS profile is a set of launch arguments under `games.rimworld.profiles` in `~/.gabs/config.json`, with its own data folder under `~/.gabs/rimworld/<folder>` (via `-savedatafolder=`). That keeps the user's normal saves and mod list untouched. A data folder holds `Config/ModsConfig.xml` (the mod list), `Config/Prefs.xml` (dev mode, window, sound) and `Saves/autostart.rws`.

- **Dev mode must be on**, because the game only honours an `autostart` save in dev mode. Profiles open straight into `Saves/autostart.rws`.
- **`-Headless`** (a Waylith flag) runs with no window or rendering. Suites take seconds. Screenshots and recording don't work, nothing that draws is exercised, and `games_stop` fails because there's no window to signal, so stop with `games_kill`. A headless profile can share its windowed twin's data folder. `-nographics` and `-batchmode` do nothing on Waylith.
- Existing profiles: `sillyanimalthings`, `sillyanimalthings-biotech`, their `-headless` twins, `sillyanimalthings-profiling` (adds DPA) and `sillyanimalthings-showcase` (1080p, no music, runs in the background). `mechupgradesui`, its `-headless` twin and `mechupgradesui-showcase` load Biotech and Mechanoid Upgrades, a Workshop mod that needs the Steam client running. `blueprintmaterials`, its `-headless` twin and `blueprintmaterials-showcase` load only Core and BlueprintMaterials. `legendaryisunique` (Odyssey) and `legendaryisunique-vse` (adds Vanilla Expanded Framework and Vanilla Skills Expanded, from the Workshop), each with a `-headless` twin, test LegendaryIsUnique without and with VSE. `tweaks` (Tweaks' hard dependencies only) and `tweaks-mods` (every mod a tweak targets, plus Transparent Substructure for the `substructure` suite; 24 mods in all, a minute to start), each with a `-headless` twin, test Tweaks. `tweaks-multifloors` and its twin add Prepatcher, MultiFloors, Better Workbench Management (Workshop; with the unofficial 1.7 port also subscribed, the port is what loads), Float Sub-Menu and Material Sub-Menu to `tweaks`, for the `levels` suite. Waylith provides Prepatcher's injected fields itself (`RimWorldWaylith.PrepatcherCompat.dll`), so mods that use them work without the Prepatcher mod. `colonistbarjobs` and its `-headless` twin load only Core and ColonistBarJobs; `colonistbarjobs-moodbar` and its twin add CM Color Coded Mood Bar (Workshop), and `colonistbarjobs-biotech` and its twin add Biotech. `saddlebound` and its `-headless` twin load Ideology and Giddy-Up 2 - Continued (Workshop). `disallowedzone` and its `-headless` twin load only Core and DisallowedZone. `blueprintmaterials-multifloors`, `colonistbarjobs-multifloors`, `mechupgradesui-multifloors` and `saddlebound-multifloors`, each with a `-headless` twin, are the mod's profile plus Prepatcher and MultiFloors (Workshop), for its `levels` scenarios. To add profiles for another mod, see [new-mod-setup.md](new-mod-setup.md).
- **A game the user started themselves (Steam) can still be driven:** RimBridgeServer's standalone direct mode starts anyway and writes its port and token in its startup lines in the game's log; connect a client to those directly. GABS's `games_connect` can't attach to it ("no runtime claim exists"), so don't make the user quit and relaunch through `main` just for that. Every game, test games included, writes the same `LocalLow\Ludeon Studios\RimWorld by Ludeon Studios\Logs\Player.log` (Waylith hard-codes it; `-savedatafolder` doesn't move it, and there's no log argument), so starting a test game loses the player's token. BridgeTools' `BridgeConnection` therefore also writes a standalone bridge's `pid`, `port` and `token` to `~/.gabs/rimworld/standalone.json`; a GABS launch doesn't touch it. Check that `pid` is the running game's. `ordo/bridge_connection` reports any game's port, token and mode. The client speaks GABP: `Content-Length`-framed JSON, `session/hello` with the token, then `tools/call` with `name` and `arguments`.
- `main` is the player's own game: no `-savedatafolder`, so their own mod list, settings and saves. It only connects when RimBridgeServer (`brrainz.rimbridgeserver`) is in that mod list. It opens at the main menu; load a save with `rimworld/load_game_ready`. **Never run scenarios or save there**: scenarios remove pawns and change the map.
- **Staying out of the user's way:** the 720p profiles open on the second monitor (`windowPositionX` 2620, `windowPositionY` 150; it starts at x = 2560 and is 1920x1080 at 100% scale), and every windowed profile has `runInBackground` on, so it runs at full speed and keeps its sound without focus. Waylith has no option to open without taking focus (GLFW's focus-on-show is set internally), so start `tools/return_focus.ps1` in the background just before `games_start`. It notes the focused window, gives focus back when a RimWorld window takes it, and watches 30 s more. On 2026-11-14 a launch while a fullscreen game had focus never took it, so the hand-back itself is still untested. The 1080p showcase profiles stay on the main monitor (`windowPositionX` 0, `windowPositionY` 38): the second monitor is too short for them once its taskbar is counted, and Windows then shrinks the window.
- Windows: a minimized window stops rendering, so the suite still passes but screenshots time out. Fullscreen windows minimize themselves on losing focus. Keep test windows at 720p, windowed.
- **Long steps are slow windowed.** `context.Step` and `step_game_ticks` advance one tick per frame, and a windowed game's frames are capped, so a scenario stepping tens of thousands of ticks takes many minutes. Meanwhile the bridge answers nothing, CPU is low and the log is quiet, which looks like a hang. On 2026-11-21 NatureTab's full suite (one scenario steps 60,000 ticks) did this twice in `naturetab`, and took 14 s headless. Run long suites headless; windowed, pass a short `suite`.
- While Windows is locked, a windowed profile can stall at "Loading game from file autostart" with idle CPU and nothing listening, so `games_connect` times out. It doesn't always: on 2026-11-15, with the lock screen focused (as `tools/return_focus.ps1` reported), the windowed `saddlebound` profile loaded, drew and took screenshots normally. If a windowed start times out, screenshot the desktop with .NET `CopyFromScreen` to check for the lock screen, then use a headless profile or wait for the user.
- `games_start` sometimes fails with "Access is denied" renaming `runtime.json`. That leaves a 30 s "starting" lease with no game running: wait and retry.

## The test save

A 33x33 map of flat soil with no pawns, things, roofs or fog, at midday. It's just big enough for one 33-cell stage site, which every scenario shares in turn.

- An empty colony gets the Stranger in Black rescue event, so `ordo/run_scenarios` and `ordo/record_showcase` turn off the storyteller and remove every pawn before starting. That lasts until the save is next loaded. **Never save after a run.**
- To make a save: with no `autostart.rws` in the profile's `Saves`, start the profile (it stops at the main menu; a `-headless` twin works too, and puts nothing on screen), then call `ordo/start_test_colony` (`mapSize` 33), `rimbridge/wait_for_long_event_idle`, `ordo/blank_map`, `ordo/set_hour` (12), and `rimworld/save_game` with **`saveName`** `autostart`. `save_game` ignores `name` and saves under a generated name.

**The error mirror:** BridgeTools copies every warning and error of each game (test games too) to `~/.gabs/rimworld/logs/<pid>.log`, starting with what the game logged before the bridge came up. It survives the next game replacing `Player.log`, and the 20 newest files are kept. Read the player's from the pid in `standalone.json`.

**Scripts in `tools/`, for when there's no GABS game:** `gabp.ps1` calls any bridge tool on the player's own game (`pwsh tools/gabp.ps1 ordo/find_things '{"match":"^Steel$"}'`, `-List` for the names); `save_query.ps1` reads things or designations per map out of a save without loading it; `mod_list_check.ps1` checks the player's mod list for missing dependencies, load-order rule violations and libraries no active mod needs.

A tool class must not be `static`: RimBridgeServer skips abstract types, and a static class is one. Use `public sealed class` with static `[Tool]` methods.

Tools that act on one mod take `mod` (packageId, name, folder or assembly name). It can be left out when only one `Ordo.*` mod with code is loaded.

Useful built-in tools: `rimworld/*` debug actions, gizmos, tick stepping and screenshots all work on 1.7/Waylith. `list_logs` reads the game log.

## The scenario suite

`ordo/run_scenarios` runs the scenarios of every running mod listed in `tools/BridgeTools/Scenarios/ScenarioSets.cs`, or of `mod`. A scenario **fails** on a broken check, an exception, any error logged to the game log, or any dialog or float menu it opened and left open, whether a message box or a mod's own window: any new window on the dialog layer counts. Errors are counted by `LogMessage.repeats`, because the log merges repeated entries.

### Writing scenarios

One scenario per mechanism and per case that behaves differently, not one per item of content. Add a final scenario that checks content wiring (for example, that every tagged race got its abilities). Each scenario is `new("name", "suite1 suite2", Run)` in the mod's `<Mod>Scenarios.All` list. `requiresAbility` skips it unless an ability def is loaded (for DLC content), and `requiresMod` unless a mod (by packageId) is active, for a mod's optional integrations. A skip shows in the results, so run the profile with the optional mod and check its scenarios passed rather than skipped. Give each one suites: one per feature, plus cross-cutting ones such as `ai`, `player`, `visuals` and `setup`.

A scenario gets a `ScenarioContext` (a `Stage` in `tools/BridgeTools/Stage.cs`):

- `Spawn(kind, x, z, PawnMode.Wild | Tamed | Trained | Manhunter | Enemy)`, `Colonist(x, z)`, `Place(thingDef, x, z)` relative to the site's origin. Spawned pawns are always adults with no old injuries, because age changes body size, which changes results. `Enemy` animals flee, so stun them to use them as targets.
- `Cast(pawn, abilityDef, target)`, `Step(ticks)`, `await Until("description", () => condition, maxTicks)`, `Check("what went wrong", passed)`, `Fail(message)`.
- **Step long spans in chunks.** In NatureTab's growth test (2026-11-20, headless), one `Step(60000)` grew a plant only about half as much as 30 calls of `Step(2000)`, which matched the game's own growth rate. Don't use a single large step when a test depends on things ticking over a long time.
- Helpers: `HasHediff`, `Hurt` (counts any injury or missing part, not only summary health), `HurtBelow`, `OnCooldown`, `Staggered`, `Terrified`, `Describe(pawn)` for failure messages.
- Buildings and mechs: `Build(thingDef, x, z, rotation, powered)` (player-owned; spawn what facilities serve before the facilities, since they link as they spawn), `Power(building, on)` (forces power on a building with no power net, which keeps it: no generator needed), `Mechanitor(x, z)` (a drafted colonist with a mechlink, added before spawning so there's no letter) and `ControlledMech(kind, mechanitor, x, z)` (a player mech the mechanitor oversees, full of energy, so it's player-controlled and uses the colony mech think tree). `Until` takes an optional `stepSize` for long waits such as fabrication.
- Player UI (from BlueprintMaterials): `Blueprint(def, x, z, stuff)` places a player blueprint; `Worker(x, z, workTypes...)` is an undrafted colonist capable of only those work types and doing only them; `Place` takes a `stackCount`. `Stage.Select(things...)` replaces the selection, and cleanup clears it. `Stage.SelectionGizmos()` is the gizmo grid for the selection, with grouped gizmos shown once. `OpenMenu(command)` clicks a `Command_Action` and returns the float menu it opened (failing if it's disabled or opens none), `MenuLabels(menu)` lists its options, and `Choose(menu, label)` picks one as a click would and closes the menu. Cleanup also removes blueprints and frames on the site.
- Cleanup is automatic: it waits for flyers to land, then destroys what the stage spawned (and discards its destroyed pawns, which would otherwise stay world pawns until the game's garbage collection) and any fire, projectiles, corpses, explosions, items and filth on the site. It also puts back what the game changes around a stage: it destroys pawns that arrived during it (wild animals spawn as time passes), deletes zones and allowed areas made during it, puts every area back as it was (the game adds home area around player buildings and zones), and restores the site's terrain (mined or destroyed rock leaves rough-hewn floor). `Place` leaves ore unowned, as natural rock is.
- **Leaks are reported.** The runner compares the map and game before each scenario with after its cleanup, and lists what changed under `leaks` on that result, with a `leaked` count: areas, zones, designations, colony buildings, pawns, terrain, roofs, fog, game conditions, weather, research, and the settings and saved game, world and map components of the Ordo mods. A leak doesn't fail the scenario, but every later one sees it, and it made NatureTab's and SillyAnimalThings' suites depend on order (2026-11-22). Put back what a scenario changes in a `finally`, as the settings scenarios do. Only the current map is checked, not MultiFloors' level maps or other maps a scenario makes.

Practices that came from real flakes:

- Wait for effects with `Until` instead of checking straight away: explosions spread over several ticks, and spray projectiles land one after another.
- On failure, report the pawns' state (`Describe`) so a rare flake can be diagnosed from one run.
- Check visual effects with scenarios (a mote appeared and went), not by eye. Motes aren't in the map's normal thing lists, so expose the last one from the mod (as `HediffComp_Overlay.LastMote` does).
- For random outcomes, such as quality rolls, wrap the loop in `Rand.PushState(seed)` and `Rand.PopState()`, so statistical checks give the same counts on every run and can't flake (LegendaryIsUnique's `craft_chance`).
- To make a vanilla call fail on purpose, such as to test a Harmony finalizer, patch it from the scenario with a temporary `Harmony` instance of its own, and `UnpatchAll` that instance's id in a `finally`. BridgeTools compiles against Harmony through `Directory.Build.props`, and the game supplies it at runtime.
- A generated colonist can be incapable of a skill, which then counts as level 0 whatever it's set to. Generate until `SkillRecord.TotallyDisabled` is false (or use `Stage.Worker` for work types).
- Prove the suite catches bugs by planting faults on purpose and checking that exactly the expected scenarios fail. Hot reload makes this quick: plant a batch of faults that hit different scenarios, make a delta, apply it and run, then revert the source and apply the reverting delta.
- Run a mod with UI windowed as well as headless. Headless, nothing is drawn, so an error in a gizmo's `GizmoOnGUI` (such as a missing texture) never happens. Keep the thing selected while stepping ticks to make the game draw its gizmos.
- Vanilla `Command.GroupsWith` already keeps apart gizmos with different icons. To test a mod's own grouping rule, use cases whose gizmos look the same (BlueprintMaterials uses granite and marble walls, both stone bricks).
- A "nothing happens" check through the think tree can pass for the wrong reason. Vanilla's `EnterBuilding` job ends at once when the building refuses the pawn, so a job giver that wrongly offered the trip still showed no trip. Call the job giver's `TryGiveJob` directly as well.
- For a MultiFloors level (in a profile with MultiFloors, with `requiresMod: "telardo.MultiFloors"`), use `UpperLevel` (`Scenarios/UpperLevel.cs`): it builds an up-stair on the site, which makes the level above, floors and unfogs (2, 2) to (13, 13) of the site around the stair's exit at (6, 6), and in `Dispose` destroys the level's pawns and zones and removes it. `Build` puts player buildings on it, and `MoveHere` moves a pawn the stage spawned up to it, drafting it again if it was. MultiFloors is reached by reflection there, so BridgeTools needs no reference to it. Leak checks don't cover the level.
- For a second map (to test what happens across maps, as after a gravship flight), generate an empty pocket map: a runtime `MapGeneratorDef` with empty `genSteps` and `pocketMapProperties { biome = map.Biome }`, and a `PocketMapParent` whose `Tile` is the first map's. `PocketMapUtility.GeneratePocketMap` leaves the tile unset, and the plant growth calculator then throws. A generation that throws after `Game.AddMap` leaves a broken map that errors every frame and blocks bridge calls, so restart. Remove it with `PocketMapUtility.DestroyPocketMap` in a `finally` (NatureTab's `filter_area_follows_the_map`).
- Map overlays drawn off the map (such as a `GenDraw.DrawCircleOutline` larger than the 33x33 test map) don't show. Scale a check down to fit on the map.
- Take the hot reload baseline (`hot_reload.ps1 -Reset`) right after each start, before editing. Once an edit is made first, the baseline would include it and the delta comes out empty, so it needs a restart instead.
- Bridge tool changes hot reload like a mod's (`hot_reload.ps1 -Project BridgeTools`, then `ordo/apply_update` with `mod: BridgeTools`). Restart for a new tool, changed tool parameters, or a new scenario or clip (see reload-and-debug.md).

## Pitfalls when driving the game

- **When `games_connect` times out, read `~/.gabs/rimworld/launch.log` first.** On 2026-11-13, a launch with the Steam client not running (`SteamAPI.Init() failed` in the log) failed to load Harmony's types: `ReflectionTypeLoadException ... RimBridgeServer: Could not load type 'HarmonyLib.CodeInstruction'`, and the mod's own Harmony patching failed too. The bridge never started. With Steam running, the same game files loaded fine. Make sure Steam is running before starting the game.
- The install is on Steam's `unstable` beta branch, so the game updates often. The test saves are from 1.7.5000 and load with a version warning, which is harmless.

- **The autosave hangs a long headless run.** On 2026-11-23, after about 75,000 ticks in one game, the autosave's synchronous long event waited for a loading screen that headless never draws. The clock stopped, every later scenario failed in under a second ("never happened within N ticks" with the tick unchanged), and `step_game_ticks` said "busy with a long event". `ordo/long_events` shows `Autosaver.DoAutosave`; call it with `markDisplayed: true` to let it run, or restart.
- **Driving the player's own game (`main`):** the bridge's map tools (`get_cells_info`, `jump_camera_to_pawn`, `ordo/things_at`) only see the current map. To see another MultiFloors level, press its level keys with `rimworld/press_key` (`N` down, `M` up, its defaults). `ordo/select` takes the id as `pawnId`, for things too. Sleeping pawns open no float menu. `rimworld/play_for` at speed 4 for 45 s ran about 50,000 ticks with 630 mods. Never save there.
- Bridge tool classes must be `public sealed class`, not `static class`, or the bridge finds no tools in them.
- Keep a mod's types out of tool method signatures and base classes in BridgeTools, so the DLL still loads in profiles without that mod. Use them only inside method bodies and scenario lambdas.
- A failed bridge call opens a blocking "attention" item: clear it with `games_ack_attention`.
- `list_logs` at `warning` is flooded by the bridge's `STARTUP_TIMING` lines: use `minimumLevel: error`.
- **`list_logs` doesn't show startup.** It reads the bridge's own journal, which starts when the bridge loads, after defs and patches. Load errors (cross-references, config errors) are in `~/.gabs/rimworld/launch.log` for the latest launch, and in game in `Verse.Log.Messages`, which a scenario can read (Tweaks' `setup_no_load_errors`). XML Extensions reports "N patch operations, 0 failed" even when what a patch produced then fails the def checks.
- **XML Extensions saves every setting on first start**, to the profile's `Config/Mod_2574315206_XmlMod.xml`. A patch's `defaultValue` only matters before that, and editing that file (with the game stopped) is a quick way to switch patches off to see their scenarios fail.
- **1.7 needs a mass on anything minifiable:** "Config error in X: is haulable, but does not have an authored mass value". A patch that makes something minifiable must add `statBases/Mass` when the def has none.
- A mod's own static constructor can queue work in a long event (Setosa's Power Tools applies weapon stats that way). Code that must see the result has to queue its own long event from `LongEventHandler.ExecuteWhenFinished`, which runs after every static constructor; the order of static constructors across mods isn't fixed.
- After a failed start with "Access is denied" on `runtime.json`, wait for the 30 s lease with a background `until` loop on the clock (foreground `sleep` is blocked), then start again.
- `screenshot_cell_rect` writes a full-window PNG to the game's `Screenshots` folder first, and can pick up a stale file with the same name. That gives an image of something else with no error, so delete the file before capturing. Each frame costs about 0.26 s whatever the window size.
- Windows paths ignore case: an output folder called `showcase` is the source folder `Showcase`.
- `claude` is at `~/.local/bin/claude.exe`, not on the tool shells' `PATH`.
